# M3.1：AI 批量整理预览、逐项批准与条件撤销

本阶段继续坚持“模型只提建议，用户决定执行”。批量建议不自动移动，任何一次确认只作用于一个明确选择的文件。上传下载、分享和旧网盘操作不依赖 AI。

## 一次生成最多四条独立建议

用户从正文检索的不同文件中选 1–4 个真实证据片段，再从自己拥有的文件夹里选择 1–12 个候选目录，明确授权发送选中片段及文件夹名给 Chat 模型：

    POST /api/v1/knowledge/assistant/move/batch/suggest
    {"sources":[{"userFileId":"101","generation":1,"chunkIndex":0}],
      "candidateFolderIds":[201,202],"consent":true}

每条单独复核实时访问权限与来源版本，并按用户设置的目录候选列表生成一个独立、10分钟有效的 ai_move_proposal。每个模型请求均计入每日 Chat 次数与 Token 用量。单项因来源过期、额度、冲突而失败时显示 SKIPPED；已经生成的建议仅停留在 PENDING 状态，不会被执行。

页面逐条展示原文件和建议目录。用户必须为每一项单独勾选批准并点击执行，再次确认窗口只针对这一项。没有“一键执行所有建议”，单项失败不使其他项目自动执行。每条执行沿用原业务移动、权限版本复核和同名检查。

## 确认撤销

只针对已批准、且记录了执行后文件更新时间快照的移动，提供：

    POST /api/v1/knowledge/assistant/move/{proposalId}/undo
    {"confirmed":true}

仅允许执行后 15 分钟内由原账号明确确认，执行状态须为 APPLIED 且尚未撤销。后端用事务与行锁检查：
- 文件仍属于当前登录用户、活跃且可用，原知识代次/片段仍存在；
- 文件名未变且仍处于此次移动的目的地，updated_at 必须等于该次实际执行后记录的值；
- 原目录仍属于当前用户、活跃且是目录，或原位置就是根目录；
- 原目录没有同名的其他活跃文件或目录。

核查通过，重新调用原 UserFileService.move 恢复原父目录，状态转为 REVERTED，保存 reverted_at。重放、跨用户、过期、文件已被人工调整或回收站、原目录删除/变化、同名冲突都拒绝；不会自动覆写。旧 M2.9/M3.0 记录没有执行后版本快照，不允许猜测式撤销。撤销操作不发送原文、不调用模型，故即使模型关闭也可以尝试在期限内恢复。

## 数据、审计与运维

Flyway V12 给 ai_move_proposal 添加 applied_file_updated_at、reverted_at 两个可空字段，旧数据保持不变。操作记录由既有 Worker 最多保存 90 天，既不保存完整模型输出，也不记录文档正文。

这不是全局目录操作日志，也不保证撤销所有可能的外部副作用。旧网盘入口缺少目录名字的数据库唯一约束，本阶段仍无法彻底排除跨 API 同时新增同名文件的竞态。要实现更严格的一致性，需要继续统一整个网盘的命名和事务策略。

AI_AGENT_MOVE_ENABLED 默认为 false。启用批量模型建议仍需已配置 Chat 模型，并由每次用户明确授权。之前的手动文件管理和索引路径保持原样。

## 验证门禁
