# M4.7：真实上传、索引 Worker 与 Staging 模型联调验收

## 本轮新增的证据层

M4.6 的真实浏览器旅程仍保留。M4.7 补足其预索引夹具未覆盖的后端链路：

`普通账号 → 上传初始化 → MinIO 两分片 presigned PUT / API 代理上传 → 合并 → 校验 Worker → AVAILABLE → FileAvailable / Outbox / RocketMQ → 解析 Worker → 关键词检索 → 人工审批整理 → 执行单项 → 取消余项 → 重读状态 → 清理本次测试项`。

脚本不插入 SQL、不调用解析器、不主动重建索引，也不以预填文本替代 Worker。一个随机文本文件为 5 MiB + 4096 bytes，使用两个直传分片；另一个小文本通过 API 代理上传。两者下载内容均核对 SHA-256。大文本允许服务端明确返回 PARTIAL，小文本必须 READY，报告保留实际状态：**PARTIAL 不代表全文完成索引**。这不是 GB 级大文件或并发压力测试。

M4.7 是 HTTP／对象存储级旅程，不伪装成浏览器上传或浏览器直传 CORS 验收。M4.6 的浏览器、移动布局与状态测试继续作为独立门禁。

## 隔离模式：CI 自动执行

`release-gate.yml` 调用可复用的 `staging-acceptance.yml`。独立 Compose 项目包含真实 MySQL、Redis、MinIO 兼容对象服务、RocketMQ NameServer/Broker、API 与 Worker，并在 `internal: true` 网络内运行 Python 验收容器。

不继承常规部署 Compose，不绑定宿主机端口，不引用外部卷或网络，不挂载 Docker socket，不使用生产凭据；模型、Embedding、Qdrant、管理员种子均禁用。CI 中的数据与账号都是随机合成测试数据，结束时移除该 run 独占项目的容器与匿名卷。中途取消仍可能留下临时项目，不能将清理未完成当成验收成功。

从仓库根目录复现（仅可信开发机／临时 CI Docker）：

```bash
set -euo pipefail
export COMPOSE_PROJECT_NAME="cc-m47-local-$(date +%s)"
export M47_IMAGE_TAG="$COMPOSE_PROJECT_NAME"
export M47_ENVIRONMENT="m47-local-$(date +%s)"
export M47_EXPECTED_SHA="$(git rev-parse HEAD)"
export M47_REPORT_DIR="$PWD/artifacts/m47"
mkdir -p "$M47_REPORT_DIR"
mvn -B -pl cloudchunk-boot -am package
docker build -f deploy/acceptance/Dockerfile.runtime \
  --build-arg REVISION="$M47_EXPECTED_SHA" -t "cloudchunk-m47:$M47_IMAGE_TAG" .
trap 'docker compose -f deploy/acceptance/compose.yml down --volumes --remove-orphans' EXIT
docker compose -f deploy/acceptance/compose.yml pull mysql redis minio namesrv broker acceptance
docker compose -f deploy/acceptance/compose.yml up -d mysql redis minio namesrv broker api worker
docker compose -f deploy/acceptance/compose.yml run --rm --no-deps acceptance
```

构建必须来自干净的待验收 checkout。Dockerfile 只给该 checkout 构建的 jar 写入 `BOOT-INF/classes/META-INF/cloudchunk-revision.txt`；它是构建身份标记，不是密码学签名或供应链证明。禁止把旧 jar 用新 SHA 重新标记。正式制品仍须使用既有摘要与发布验证流程。

## Staging 模式：人工授权，不自动部署

**执行脚本不部署 API／Worker，不设置 GitHub 服务器端环境保护，不创建模型供应商账号，不自动触发收费调用。** 必须先由维护者部署待验收候选版本，再触发手工工作流。普通 PR／push 只运行隔离模式，不能获得 Staging secrets。

创建 GitHub Environment `staging-acceptance`，配置 required reviewers、禁止自审批和仅 main 分支的部署限制。`environment:` 声明本身不等于审批保护已配置。工作流只允许 main 上的显式 dispatch；远程作业串行且不自动取消，避免相互污染测试与不明确写入。

Environment variables：`STAGING_API_ORIGIN`、`STAGING_STORAGE_ORIGIN`（均为精确 HTTPS origin，无路径、用户信息、查询参数）、`STAGING_ACCEPTANCE_ENVIRONMENT`（例如 `m47-staging-01`）。

Environment secrets：`STAGING_ACCEPTANCE_ACCOUNT`、`STAGING_ACCEPTANCE_PASSWORD`、`STAGING_ACCEPTANCE_OTHER_ACCOUNT`、`STAGING_ACCEPTANCE_OTHER_PASSWORD`。两个账号必须不同、名称以 `m47_` 开头、不是 ADMIN，且根目录为空；请使用专用测试账号，禁止真实用户账号。

仅在 Staging API 上增加 `acceptance` profile，并明确设置：

```text
SPRING_PROFILES_ACTIVE=api,acceptance
CLOUDCHUNK_ACCEPTANCE_ENABLED=true
CLOUDCHUNK_ACCEPTANCE_MODE=staging
CLOUDCHUNK_ACCEPTANCE_ENVIRONMENT=m47-staging-01
```

正常 API 认证仍然生效。`/api/v1/acceptance/identity` 是只读 no-store 端点；缺少 profile 或显式 enable 时不存在；同时启用 `prod`／`production` profile 时也不存在。启用验收但 jar 缺少有效版本标记会启动失败，不能用环境变量伪造版本返回值。禁止在生产打开 acceptance profile；profile 名称并不能识别一个被错误配置的生产环境。

手工 dispatch 输入的 origin 必须与预设环境 allowlist 一致，`candidate_sha` 必须是已部署制品中的完整提交号，`confirm` 必须为 `WRITE_SYNTHETIC_STAGING`。身份不匹配、非空账号、清理失败、任何关键阶段缺失均失败。Staging 应让 API 与 Worker 使用同一不可变镜像摘要；当前 identity 端点只证明所请求 API 的标记，不独立证明 Worker 的制品版本或后端拓扑。

## 真实模型可选验收

默认 `live_model=false`，报告明确是 `model: not-requested`，绝不能据此宣称真实模型通过。

要求真实模型时设置 `live_model=true`、`model_consent=ALLOW_TWO_SYNTHETIC_MODEL_CALLS`。模型供应商 endpoint、model、API key 只在 Staging 服务端配置，CI 无需获取供应商 key。服务端需启用 `AI_CHAT_ENABLED` 与 `AI_AGENT_MOVE_ENABLED`；专用测试账号剩余 chat 调用额度至少为 2。

只发出两次模型请求：一次带来源引用的问答、一次只有本轮新建目标文件夹作为候选的移动建议。均只传合成文本与合成文件名。随后创建单步 Agent 计划，批准后验证仍未移动，单独执行并验证目标位置，再调用条件撤销并验证原位置。按 UTC 日比对服务端 attempted call 计数差必须等于 2；跨日或账号被其他请求使用会失败。

不重试模型请求，不绕过额度，不接受无引用回答；供应商故障、模型拒绝建议或引用验证失败均为验收失败。attempted call 不是最终供应商账单，也不是模型答案全面质量评测。是否实际连接外部真实供应商由受控 Staging 配置保证；未运行该 lane 时不得填造供应商成绩。

## 报告、预算与清理

`isolated.json`／`staging.json` 记录环境、精确提交号、各阶段耗时与通过状态、实际索引状态、模型执行状态、清理状态。启动前先覆盖旧成功报告，日志仅固定错误码；不写入密码、Bearer token、presigned URL、请求体、回答正文或供应商 key。

每个上传阶段预算 180 秒，索引阶段 125 秒，单次模型阶段 35 秒，其余各阶段 120 秒；HTTP 单次超时 30 秒。预算是测试阻断值，不是生产性能成绩。后台就绪只重读，不重试写入。总运行时间同时受 workflow timeout 限制。

清理仅对本次已收到回执、名称仍匹配随机前缀的文件项执行既有软删除；目录必须确认无子项后才删除；规则停用并注销会话。不会按前缀批量扫除，不递归删除不认识的子项，不硬删审计／历史／回收站。上传结果不明确、缺失回执或并发更名时报告 incomplete，需维护者在专用账号核对遗留数据。Staging 回收站、派生索引／对象 GC 与审计保留仍按原系统策略处理；cleanup complete 不表示所有存储物理字节或历史记录已抹除。

复测失败不要放宽阈值、跳过步骤或替换报告。先依据失败阶段核对对象存储、队列消费者与权限。回滚镜像不恢复已经移动的用户文件；应先核对回执并使用现有条件撤销。

## 发布候选判定

必须分别检查 M4.6 浏览器结果、M4.7 隔离上传 Worker 结果、候选版本 Staging 结果；发布 AI 功能还需对应版本真实模型 lane。任何未执行项保持未验收，不得因其他任务绿色而推断它通过。
