# M3.0：归类候选文件夹、冲突检查和操作历史

本轮保持之前的安全约束：模型仅能从当前用户授权的正文和经后端验证的目录中提出一个建议。执行仍需浏览器的二次确认；服务端检查业务 ACL、文件与目录状态、版本和提议是否尚未使用。

## 选择候选文件夹

M2.9 按文件夹 ID 取前 12 个，可能错过更相关的目录。M3.0 改为先由用户在资料工作台选择最多 12 个目标文件夹。新接口：

    GET /api/v1/knowledge/assistant/move/folders?userFileId={当前文件的逻辑节点ID}

返回最多 100 个用户拥有的活跃文件夹，按文件夹名、ID 排序；当前父目录自动剔除。超过 100 个时响应 hasMore=true，界面标明前 100 个的限制。获取目录不发送模型请求、不消耗模型额度。请求会先核对来源文件用户归属、可用状态和知识索引 READY/PARTIAL。

请求建议时使用：

    POST /api/v1/knowledge/assistant/move/suggest
    {"source":{"userFileId":"101","generation":1,"chunkIndex":0},
     "candidateFolderIds":[201,202],"consent":true}

后端最多接受 12 个不同且正整数的目录 ID。每一个都再次按当前用户、活跃状态和目录属性读取，拒绝不存在、回收站、跨用户、文件节点和当前目录。候选的次序由用户提交，不以模型文本指定路径。模型只需返回当前候选列表中的序号和引用编号。旧客户端不提供 candidateFolderIds 时仍可回退原先按 ID 排序的 12 个目录，保持向后兼容。

## 移动同名冲突处理

在模型生成建议后、保存提议前及确认实际执行前，后端检查同一用户目标文件夹是否有同名的活跃文件/文件夹。发现冲突直接拒绝，不覆盖目标条目，不复制文件，也不自动加后缀。确认执行失败不会将提议标为 APPLIED；用户可以先人工处理冲突，再重新获取建议。

这项检查和对目的目录的行锁只能覆盖已有记录与参与本操作的并发；**由于原有网盘没有全局 (user_id,parent_id,file_name) 唯一数据库约束，无法承诺排除所有跨 API 并发重名竞态**。若需严格唯一性，需要后续统一普通移动、上传、复制与重命名的约束或事务策略。

## 历史

资料工作台新增“AI 文件整理记录”。它是用户主动展开的只读面板，会读取：

- GET /api/v1/knowledge/assistant/move/recent
- GET /api/v1/knowledge/assistant/rename/recent

每种最多显示最近 10 条，包含建议的前后变化、应用状态及到期时间。只在当前认证账号范围内查询，不发送原文到模型，不为历史提供绕过确认的直接应用按钮。未执行的提议可能已过期或因文件变化而不可用，页面明确标注不能保证仍可执行。

## 验证范围

GitHub CI 的真实 MySQL Testcontainers 测试覆盖目录枚举不得泄露其他用户目录、显式候选 ID 的重复/跨用户拒绝、保存后新增同名文件时禁止执行、冲突没有消耗提议、原来重放与回收站路径仍被拒绝。前端 npm run build 和检索评测单元测试继续作为必过门禁。生产部署仍需在管理员启用 AI_AGENT_MOVE_ENABLED=true 且 Chat 模型可用后使用，不会自动执行文件变更。
