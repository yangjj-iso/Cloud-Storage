# M4.3：用户授权的整理策略推荐与反馈闭环

> 本阶段将 M4.1 的安全 AI 文件移动建议与 M4.2 的可保存整理规则连接起来。模型不会获得文件操作工具，推荐本身不移动任何文件，人工“有帮助”反馈也不等于同意执行。上线前仍须通过 MySQL/Flyway V16 迁移、数据库备份和生产等价环境验收。

## 一、用户流程

1. 用户先在 **AI 工作台 → 整理策略** 保存属于当前账号的整理模板，目标必须是自己的有效目录。
2. 在 **AI 工作台 → 搜索与问答** 中先检索本人可访问的索引正文。在结果下方选择一份实际证据片段和最多 **8 条自己的模板**。每个目标目录最多只允许一个模板，避免模型序号与模板对应关系产生歧义。
3. 用户**明确勾选一次性授权**，说明已选原文和候选目录名可能发送至部署方配置的外部 Chat 服务；提交后无论成功或失败均清除本次授权。每天模型请求量由既有 `AiDailyCallBudget` 数据库配额限制。
4. 服务端首先按**当前文件 ACL、文件当前 AVAILABLE 状态、知识索引 generation、文件 MIME 与模板规则**检查所有候选，任何模板不属于当前用户、目录无效、同一目录重复或 MIME 不符合均拒绝整次请求；不会调用模型。随后调用原有 `AiMoveAgentService.suggest`，沿用已有证据重新鉴权、候选目录编号限制、模型输出严格格式和推理后冲突校验。
5. 推荐成功只返回一个关联已存在移动建议的**候选整理模板**；用户可以选择「有帮助」（接受反馈）或「不采纳」并指定固定拒绝原因。不能把提示词、文件正文、自由文本拒绝理由或模型输出存入反馈记录。
6. 如要真正整理文件，用户需要另行前往 **整理策略**，重新选择文件并进行 M4.2 冲突模拟，再逐项批准和执行。不会从建议或反馈页面自动发起移动，也不复用已过期的模型建议来绕过确认。

## 二、接口

所有端点均在 `/api/v1/knowledge/assistant/strategy` 下，使用现有登录用户权限以及 `Cache-Control: no-store`：

| 方法 | 子路径 | 说明 |
| --- | --- | --- |
| `POST` | `/recommend` | `{source:{userFileId,generation,chunkIndex},templateIds:[...],consent:true}` |
| `POST` | `/recommendations/{id}/feedback` | `{decision:"ACCEPTED",reasonCode:"USEFUL",confirmed:true}` 或 `{decision:"REJECTED",reasonCode:"WRONG_FOLDER",confirmed:true}` |
| `GET` | `/recommendations` | 最近 15 条本人仍有活动文件引用的推荐；不包含原文 |
| `GET` | `/quality` | 当前账号近 30 天接受、拒绝、待反馈次数及有条件展示的反馈接受率 |

反馈拒绝原因固定为：`WRONG_FOLDER`、`WRONG_CATEGORY`、`INSUFFICIENT_CONTEXT`、`OTHER`。接受反馈只允许原因 `USEFUL`。每条只能在**创建后 24 小时内**从 `PENDING` 状态写入一次反馈；重复提交、更改已录入的结果、其他用户写入或无确认标志会失败。

这里的接受比例 = 当前账号近 30 天主动接受数量 ÷ （主动接受+主动拒绝数量），**有效评价少于 5 次不显示比例**。它只是操作人主观反馈，**不是模型客观准确率、业务成功率或自动在线学习效果**。没有任何把评价转交到外部模型微调训练的行为，数据仍由当前数据库持有。

## 三、权限与隐私

- 强制使用 **规范十进制字符串** 表示原文逻辑文件 ID，拒绝前导零、非法格式、超范围和无效版本。最多 8 条唯一模板 UUID，严格按当前 owner 查询；不能把别人模板带入模型候选。
- 每个模板的规则类型需与数据库可信 MIME 一致，目标是当前用户有效目录且不是文件已所在的目录。历史模型建议的原文/文件路径、原始模型返回文本和 Provider URL **不会保存在 M4.3 反馈表**。
- 用户仅授权本次明确选定的来源证据段，模型没有目录读写、删除、归档或任意 shell/HTTP 工具。现有 AI Move Agent 会在模型推理之后再核验来源及目标快照，防止推理期间的撤权和并发修改。
- 无需启用模型时，原来的 **M4.2 确定性 MIME 规则和冲突模拟**仍可独立使用；AI 功能因部署方未配置模型或禁用移动 Agent 而不可用时，会明确返回功能未启用，而不是悄悄发起请求。
- 通过 MySQL V16 保存私有推荐 ID、用户 ID、模板引用、既有移动建议 ID、逻辑文件引用、反馈状态/原因代码与有限时间戳。没有文件正文、模型 prompt/回答、用户自由反馈、API 密钥和外部 Webhook。
- 评价一个推荐**不是批准执行**。现有移动 API 仍有独立确认、过期、来源代际、冲突和权限边界。

## 四、上线与验证

新增 Flyway **V16**：`ai_strategy_recommendation` 单表，提议映射唯一索引 `uk_strategy_recommendation_proposal`（一个底层建议不能生成多个反馈映射）以及模板和既有提议的外键。发布前的只读检查增加 V16 成功迁移、表存在和唯一索引校验，保留 V13–V15 以及已有恢复验收的全部门禁。

```bash
python3 -m unittest discover -s deploy/preflight/tests -v
mvn -B verify
cd cloudchunk-web && npm ci && npm run build
```

新增 Java 单元测试验证显式授权、输入格式、候选上限和模型禁用；真实 MySQL Testcontainers 集成回归验证跨账号模板、MIME 不匹配的请求不能调用模型、推荐映射正确、他人不能评价、反馈只能执行一次、反馈质量不显示低样本比例以及原始文件被移入回收站后历史不应泄漏。

CI 的模型部分采用**受控 Mock**，不执行真实有费用的模型调用；真实模型提供商的调用延时、答案质量及用户主观评价，需要在专用测试账号上另行验收。正式启用前仍须备份、批准 V16 迁移、运行验收脚本并检查开发与生产功能开关和每日预算。

## 五、下一步

建议 M4.4 增加更完善的引用证据展示、可复现的推荐质量评测集、匿名聚合质量指标、数据保留清理策略和更系统的用户授权审计。**M4.3 不做自动学习、自主文件移动、无审批批量执行或生产线上直接运行故障注入。**
